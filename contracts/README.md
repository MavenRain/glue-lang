# glue-lang verifier contracts

A Foundry project for the Solidity verifier that `glue-halo2 solidity`
writes. There is one verifier for each example circuit of
`test/circuit/expect.txt` in the repository root: `square`, `range`,
`poly`, `nonzero`, `poseidon`, `transfer`, `kyc` and `kycMerkle`. `make e2e` writes them.

## Files

- `src/verifiers/NAME.sol`: generated by `glue-halo2 solidity`. Do not
  edit. Each file has a contract `Halo2Verifier`. The verifying key is in
  the contract, so there is one contract to deploy for each circuit.
- `test/fixtures/NAME.proof.json`: written by `glue-halo2 prove` with the
  same keys. The prover is randomized, so each `make e2e` writes a new
  proof.
- `test/Verifiers.t.sol`: one test contract for each circuit. The valid
  proof verifies. Each tampered instance, each instance not below r, a
  wrong instance count, a tampered proof and a truncated proof are
  rejected (revert or false). The CLI calldata is the ABI encoding of
  `verifyProof(proof, instances)`. The public inputs are those of
  `test/circuit/expect.txt`.
- `test/Vm.sol`: the few Foundry cheat codes that the test and the script
  use. The project does not use forge-std.
- `script/DeployVerifier.s.sol`: `--sig 'run(string)' NAME` deploys the
  verifier of the circuit NAME and logs its address. The script reads the
  creation code from the build artifact (`getCode`) and does not import the
  verifiers. A NAME with no artifact stops the script.
- `src/KycGate.sol`: the admission policy of docs/M9-PLAN.md D7 in front
  of one kyc or kycMerkle verifier (`## KycGate` below).
- `test/KycGate.t.sol`: the tests of the gate against the kyc and
  kycMerkle fixtures.
- `script/DeployKycGate.s.sol`: deploys a gate in front of a deployed
  verifier.
- `script/rehearsal.sh`: the anvil rehearsal of the deployment (D6).
- `script/check.sh`: the read-only checks of a deployment (D6).

## Interface

    function verifyProof(bytes calldata proof, uint256[] calldata instances)
        public view returns (bool);

The selector and the ABI are those of docs/IR.md section 5. The generator
writes `public view`. The contract returns true or reverts. `instances` is
instance column 0, in row order. The verifier requires the canonical ABI
layout emitted by the CLI and rejects redirected argument offsets.

## Regenerate

Run `make e2e` from the repository root. For one circuit, the steps are in
the root README.md (section Pipeline). Use the same keys directory for
`solidity` and `prove`, or the proof does not match the verifier.

`--dev-srs` is INSECURE. It is for local tests only. For a real deploy,
use `--srs FILE --sha256 HEX` with a KZG params file from a trusted setup
and its pin. The rule `make e2e-ceremony` does this for each example
circuit (the next section).

## The ceremony SRS

`make e2e-ceremony SRS=FILE` runs the chain of `make e2e` for each example
circuit with the ceremony SRS in FILE in place of the development SRS. The
keys, the proofs and the verifiers go to `build/e2e-ceremony/` (the
verifiers to `build/e2e-ceremony/verifiers/NAME.sol`). Nothing under
`contracts/` changes, and the rule does not run Forge.

The back end checks the file before it reads it. `keygen --srs FILE
--sha256 HEX` computes the SHA-256 of FILE and refuses the file when the
digest is not HEX. The pin is the first word of `halo2/ceremony.sha256`
(the `shasum -a 256` form). The rule gives that pin to each `keygen`.

The pinned file is `kzg_bn254_15.srs`: k 15, the halo2 KZG params layout
(PSE halo2 v0.3.0), from
https://axiom-crypto.s3.amazonaws.com/challenge_0085/kzg_bn254_15.srs, a
copy of the perpetual powers of tau, challenge 0085. The file is not in
the repository. Keep it outside the repository or under `build/`.

A ceremony SRS changes the G2 points and the verifying key of each
verifier. A ceremony verifier is not the verifier in `src/verifiers/`, and
the tests here stay on the development SRS. A real deploy uses a verifier
from `build/e2e-ceremony/verifiers/` (M9 s6).

## Deploy on a local anvil

In one terminal:

    anvil

In a second terminal, with one of the private keys that anvil prints:

    forge script contracts/script/DeployVerifier.s.sol --root contracts --sig 'run(string)' square \
        --rpc-url http://127.0.0.1:8545 --private-key $ANVIL_KEY --broadcast

Call the verifier with the CLI calldata. The result is 1 (true):

    cast call $VERIFIER $(jq -r .calldata contracts/test/fixtures/square.proof.json) \
        --rpc-url http://127.0.0.1:8545

## KycGate

`src/KycGate.sol` is the admission policy of docs/M9-PLAN.md D7 in front
of one kyc or kycMerkle verifier. The verifier, the scope and the minimum
are fixed at the deploy. The issuer approves an anchor: the commitment cm
of a credential (kyc) or the root of a credential tree (kycMerkle). A
revoked anchor is refused. `admit(proof, instances)` takes the five public
inputs in the circuit order: anchor, nf, scope, min, sender. The sender is
the caller's address as an unsigned integer. A wrong count, an anchor
that is not approved, another scope or min, a sender different from
`msg.sender` and a used nullifier are refused before the verifier runs.
A rejected proof reverts with
ProofRejected and records nothing. An accepted proof records nf, so the
same credential is admitted one time at this scope (the replay guard). The
caller chooses no anchor, scope, min or sender. The constructor refuses a
scope at or above r and a min above r - 256 (the D1 range bound). The
proof binds the sender, so a relayer cannot admit another holder's proof.

`test/KycGate.t.sol` tests the gate against the kyc and kycMerkle fixtures
(12 tests). `script/DeployKycGate.s.sol` deploys a gate. `script/rehearsal.sh`
and `script/check.sh` are the D6 rehearsal and the read-only checks of the
runbook below. After building the ceremony artifacts, `make deployment-test`
checks that an occupied rehearsal port receives no transactions, that
deployment checks reject a missing or unexpected issuer, and that the
proof sender can differ from the issuer. Checks leave the nullifier unused.

## The deployment runbook

The target network is a parameter: nothing in the repository names a
chain, a URL or a key. Set the five values in your shell. They stay
outside the repository.

    NETWORK=<the network name>
    CHAIN_ID=<the chain id>
    RPC_URL=<the RPC URL>
    EXPLORER=<the explorer URL>          # VERIFY_URL=<its verify-source endpoint>, or none
    ACCOUNT=<the keystore account name>  # cast wallet import $ACCOUNT --interactive, one time

1. Build the ceremony verifiers with the pinned SRS file (docs/M9-PLAN.md
   D5):

       make e2e-ceremony SRS=FILE

   The verifiers are in build/e2e-ceremony/verifiers/ and the proofs in
   build/e2e-ceremony/NAME-proof/. The `ceremony` profile of foundry.toml
   compiles them: `FOUNDRY_PROFILE=ceremony forge build --root contracts`.
   contracts/out stays the development build.

2. Rehearse on a local anvil with the chain id of the target (D6):

       make rehearsal CHAIN_ID=$CHAIN_ID

   It deploys the kycMerkle verifier and a KycGate (scope 9, min 18, the
   fixture root approved) from an anvil account that is unlocked in the
   node, then runs the checks of step 5. `NAME=kyc` rehearses the kyc
   verifier. RPC requests use a unique IPC socket belonging to that anvil;
   an existing server on PORT receives no calls. Exit 0 is the go.

3. Deploy the verifier. Simulate first (no `--broadcast`), then broadcast:

       FOUNDRY_PROFILE=ceremony forge script contracts/script/DeployVerifier.s.sol --root contracts \
           --sig 'run(string)' kycMerkle --rpc-url $RPC_URL --account $ACCOUNT
       FOUNDRY_PROFILE=ceremony forge script contracts/script/DeployVerifier.s.sol --root contracts \
           --sig 'run(string)' kycMerkle --rpc-url $RPC_URL --account $ACCOUNT --broadcast

   The log line `kycMerkle verifier 0x..` gives VERIFIER.

4. Deploy the gate. ISSUER is the address that approves anchors, SCOPE and
   MIN are the credential policy, ANCHOR is the first public input of the
   credential proof (or 0: approve later with `approve(anchor, true)` from
   ISSUER). The approve in the script needs ISSUER = the broadcaster.
   Simulate first, then broadcast:

       FOUNDRY_PROFILE=ceremony forge script contracts/script/DeployKycGate.s.sol --root contracts \
           --sig 'run(address,address,uint256,uint256,uint256)' $VERIFIER $ISSUER $SCOPE $MIN $ANCHOR \
           --rpc-url $RPC_URL --account $ACCOUNT
       FOUNDRY_PROFILE=ceremony forge script contracts/script/DeployKycGate.s.sol --root contracts \
           --sig 'run(address,address,uint256,uint256,uint256)' $VERIFIER $ISSUER $SCOPE $MIN $ANCHOR \
           --rpc-url $RPC_URL --account $ACCOUNT --broadcast

   The log line `KycGate 0x..` gives GATE.

5. Check the deployment. The checks are read-only (`cast call` and
   `cast code`):

       make deploy-check RPC_URL=$RPC_URL CHAIN_ID=$CHAIN_ID VERIFIER=$VERIFIER GATE=$GATE ISSUER=$ISSUER SCOPE=$SCOPE MIN=$MIN

   It compares the verifier code with the ceremony artifact, calls the
   verifier on the ceremony proof, checks the gate's issuer and policy
   parameters, and runs the admission as an eth_call. ISSUER is required
   when GATE is supplied. The admission call sets `--from` to the sender
   in the proof's fifth public input. It needs no key and sends nothing.
   Build a holder's proof with `sender=` set to that holder's address as
   an integer; the example proofs use anvil account 0.

6. Publish the source on the explorer when it has a verify endpoint (add
   `--verifier blockscout` for a Blockscout explorer; the default is the
   Etherscan form):

       FOUNDRY_PROFILE=ceremony forge verify-contract --root contracts --chain $CHAIN_ID \
           --verifier-url $VERIFY_URL $VERIFIER ../build/e2e-ceremony/verifiers/kycMerkle.sol:Halo2Verifier
       FOUNDRY_PROFILE=ceremony forge verify-contract --root contracts --chain $CHAIN_ID \
           --verifier-url $VERIFY_URL $GATE src/KycGate.sol:KycGate \
           --constructor-args $(cast abi-encode 'constructor(address,address,uint256,uint256)' $VERIFIER $ISSUER $SCOPE $MIN)

7. Admit a holder. The holder's address is the fifth public input of the
   credential proof (`sender=` as an unsigned integer), so the admission
   transaction comes from that address: the gate reverts with `WrongSender`
   for any other sender, a relayer included. PROOF_BYTES is `.proof` and
   INSTANCES the five `.instances` of the holder's proof.json as decimals
   (the form that check.sh builds). Simulate with `cast call --from` first:

       cast call $GATE 'admit(bytes,uint256[])(uint256)' $PROOF_BYTES "[$INSTANCES]" \
           --from $HOLDER --rpc-url $RPC_URL
       cast send $GATE 'admit(bytes,uint256[])' $PROOF_BYTES "[$INSTANCES]" \
           --rpc-url $RPC_URL --account <the holder's keystore account>

   The gate records the nullifier: the same credential is admitted one
   time at this scope.

The bytecode targets EVM paris (no PUSH0), so it runs on chains that do
not have Shanghai. `## Deploy on a local anvil` above is the development
verifier; this runbook is the ceremony verifier.
